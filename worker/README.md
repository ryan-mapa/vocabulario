# Vocabulario Worker

Cloudflare Worker + D1. Serves the app **and** the API from one origin, so the
whole thing is a single deploy on a single address.

Live at <https://vocabulario.ryan-mapa.dev>.

Signing in is optional and always will be. Signed out, the app runs entirely on
`localStorage` exactly as it did before this existed — an account only adds
progress that follows you between devices.

## Layout

`wrangler.toml` sits at the repository root rather than in here, because the
app's static files are the repository root: the same files GitHub Pages serves,
with no build step between them and the browser. `.assetsignore` names
everything that must *not* be uploaded — git history, tests, tooling,
`node_modules`, and this directory.

That list is the thing to be careful with. Anything not named in it becomes a
public URL on the site.

```
wrangler.toml            config, at the repo root (assets dir is ".")
.assetsignore            what must never be uploaded
worker/src/index.js      routes
worker/src/auth.js       HMAC-SHA256 JWT on Web Crypto
worker/migrations/       D1 schema, applied in order
```

## Endpoints

Any request matching a file is served as a static asset first; these routes
handle what is left.

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/me` | Whether this browser is signed in, and as whom. |
| `GET` | `/auth/google/start` | Begin Google OAuth. |
| `GET` | `/auth/google/callback` | Finish it, set the session cookie, redirect home. |
| `POST` | `/auth/logout` | Clear the session cookie. |
| `POST` | `/sync` | Push this device's answers, pull every device's cards. Requires a session. |

## Sync

One request does both directions, and the order is the point: the pushed
reviews are folded *before* the pull reads, so the cards coming back already
include what was just sent and can never be a step behind it.

```
POST /sync  { since, reviews[], imports[], rounds[], days[] }
         -> { serverTime, accepted[], acceptedRounds[], cards{}, days{} }
```

`since` is the client's last `serverTime`; `0` asks for everything, which is
what a browser signing in for the first time sends. The response carries every
card whose `updated_at` is newer than `since` — including the words just
pushed, since re-folding stamps them.

**A first sync sends `imports` and no `reviews`, deliberately.** Progress
earned while signed out exists in two overlapping forms in the browser: the
card map, and the queued answers that produced it. Sending both would fold
those answers on top of a snapshot that already contains them and promote every
word a second time. The snapshot wins, because it also covers progress from
before answers were ever recorded; granular history starts from the account.

`imports` is `INSERT OR IGNORE`, so the first snapshot for a word is the one
that counts. A second browser signing in later does not overwrite it — its real
answers are folded on top instead.

`rounds` carries a `localDay` stamped by the browser, and the server stores that
string without ever deriving a day from a timestamp — its idea of "today" is not
the learner's. `days{}` comes back as a `GROUP BY local_day` across every
device, and the streak is computed from it in the client. There is no streak
counter here to fall out of step.

`days[]` is the same handover as `imports`, for day counts earned before there
was an account. Each becomes placeholder round rows whose ids are derived from
the date, so re-sending the handover inserts nothing new — idempotence is a
property of the id, exactly as it is for reviews.

## The data model

The schema is deliberately inverted from the way the browser stores progress.

`reviews` is **append-only and is the source of truth**: one row per answer,
never updated, never deleted. `cards` is a **fold over it** — derived, and safe
to drop and rebuild at any time.

Two things follow from that, and they are the reason it is built this way:

- **A new statistic can always be derived from an event log**, but history that
  was never written cannot be recovered. Changing the scheduling algorithm
  later is a re-fold, not a reset.
- **Two devices merge without a conflict.** `reviews.id` is generated by the
  client, so a retried upload collides on the primary key and is ignored rather
  than double-counted; the log is a set union and the fold is deterministic. A
  review arriving late from another device just re-orders correctly on the next
  fold. There is no last-write-wins, and so nothing to lose.

The fold must sort by `(reviewed_at, id)`, not `reviewed_at` alone — two
devices can produce answers in the same millisecond, and without the tiebreak
they would disagree about the same history.

`word_es` is the Spanish string, the same progress key the browser already
uses. It is not a foreign key: the word list lives in a static file, and a
`words` table would have to be re-synced on every deploy. The cost is that
renaming a word orphans its rows — but unlike `localStorage`, here that is
repairable with an `UPDATE`.

## Deploying

```sh
npm run deploy
```

Deploys are manual. Nothing in this repository triggers one, so the live site
is whatever `wrangler deploy` last uploaded.

## Secrets

Three, set from your own terminal so they never land in a transcript. They take
effect immediately — no redeploy.

```sh
openssl rand -base64 48 | npx wrangler secret put JWT_SECRET
npx wrangler secret put GOOGLE_CLIENT_ID
npx wrangler secret put GOOGLE_CLIENT_SECRET
```

The first pipes in, so the signing key is never displayed or kept in shell
history. Until `GOOGLE_CLIENT_ID` is set, `/auth/google/start` answers `503`
rather than redirecting somewhere broken.

sushi48 uses a fourth, `IP_SALT`, to salt hashed IP addresses for rate-limiting
anonymous score posting. Every write here is authenticated, so limits are
per-user and there is nothing to salt.

## Google sign-in

The OAuth client lives in its own Google Cloud project, not sushi48's. Clients
are per-project but the consent screen is not, so sharing a project would show
everyone a screen reading "Sushi48".

- Redirect URI: `https://vocabulario.ryan-mapa.dev/auth/google/callback` —
  exact, no trailing slash. A mismatch fails at first sign-in with
  `redirect_uri_mismatch`, not at setup.
- Scopes: `openid profile` only. **No email is requested or stored.**
- Authorized domain `ryan-mapa.dev` is verified against the Google account via
  a TXT record on the apex. **Leave that record in place** — Google re-checks
  it and un-verifies the domain if it disappears.

Staying on **Testing** publishing status is fine indefinitely: it allows 100
users, and its 7-day refresh-token expiry does not matter because the code is
exchanged once at sign-in and the session then runs on this Worker's own 30-day
cookie. Publishing would need `/privacy` and `/terms` pages, but would not
trigger Google's verification review — that is only for sensitive scopes.

## Local development

```sh
npm run db:local     # apply migrations to the local D1
npm run dev          # app + API on http://localhost:8787
```

`.dev.vars` holds local values for the three secrets and is gitignored.
**Wrangler only reads it at startup**, so restart after editing it.

OAuth will not complete against localhost unless a redirect URI pointing there
is registered on the Google client. To exercise a signed-in path without that,
mint an HS256 JWT with the same `JWT_SECRET` (payload `{ sub, name }`), insert
a matching `users` row, and send it as a `vocabulario_session` cookie.

Local and remote databases are entirely separate stores.

## Notes

- The session cookie is `HttpOnly; Secure; SameSite=Lax`. Lax rather than
  Strict because the browser returns from Google by a top-level redirect, which
  Strict would withhold the cookie on.
- `workers_dev = false` and the custom domain mean there is no second URL to
  keep working. Every top-level key in `wrangler.toml` must sit **above** the
  first `[section]` header — TOML assigns any key after a header to that table,
  so a misplaced `workers_dev` silently becomes `assets.workers_dev` and is
  ignored with only a warning.
